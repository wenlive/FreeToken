## 修复范围

验证图按声明的物理 W 捕获，以有效行数屏蔽块尾 KV 写入、路由和提交，避免输出长度变化时每个短尾重新捕获。
两个前缀、W8/16/32 的全部 112 个有效尾长已审计：不新增图，live GDN 状态不变，有效 logits 和逐层事务状态
与相同物理 W 的完整参考逐元素相同。这个参考不是旧的未填充单行 MMVQ，二者数值路径不同。
preview 不写模型 KV/GDN；verify 只写已分配的有效 KV 行，GDN 则在显式 commit 后才前进。

selfspec 验证惩罚按行累计假设提交，融合 argmax 与接受前缀计算，一轮回读一份小结果；
causal 复用 GPU 惩罚状态，避免每 token 重建历史。保留 Torch 参考用于数值检查。
实现中专门对齐 Torch 的 repetition penalty 标量倒数舍入，不能仅用数学等价的除法替换。

自动规划为 `(W+1) × 单份 GDN 状态 + 5 字节` 预留事务及 clean 状态：
W32 共 2,124,840,965 字节。startup admission 与重建使用同一持久预算基准；
新 prefill 不再释放下一轮已承诺的事务窗口。Q8 自动 .9、4K KV 的生命周期实验分配 2292 个专家槽，
经历 W32、742-token 新 prefill 和 selfspec16 后仍保留同一窗口；NVFP4 同类核查也通过。

另外修复 Q8 专家行尺寸表（实际 3,342,336 字节/专家），AOT 保留各已支持混合类型尺寸；
元数据锁页 packet 采用双缓冲和 event 保护；capture 检查真正写入的层集合，replay 恢复该集合，
不再无条件把所有层标为已写。

## 去噪的条件成本预算

本节固定 cap64，与 R0 HF LowConfidence 记录相同，P1，Q8 2560 槽；
这里的 HF 是 R0 使用相同官方 Q8 权重的独立数学参考（精确反量化、Q8_1 激活），不是原始 BF16 权重跑分。
分别记录 preview、verify、state_commit、save_ahead、advance 和外层 round 的 CUDA event 区间。
事件区间不是纯 kernel 时间，也不是硬件利用率；轮内主机等待造成的空隙会反映在外层 round 中。
插桩数据单列，不混入上面的无插桩矩阵。

设 HF 可见输出 N_H、预览 P_H、块数 B_H；原生平均预览 p、平均整块提交 c。
HF 条件预算为 `N_H / (P_H × p + B_H × c)`。
原生进度预算为 `N_native / (Σpreview + Σverify + Σstate_commit + Σsave_ahead)`。
实测生成轮吞吐为 `N_native / (Σround - Σadvance)`。
“自身成本达成率”为这些计算区间总和除以生成轮区间总和；它只评价这个计时边界内的额外成本，不能解释成整机效率。
把原生平均 p/c 复用于 HF 轨迹是反事实估算，没有逐步强制相同路由/缓存，因而不是严格上界。
p/c 封套内部也包含主机提交造成的等待；约 99% 只说明这些封套覆盖了大部分轮内时间，不证明 Python 开销已经全部消除。

| Q8 W16 提示 | HF 可见 token/预览 | p ms | c ms/块 | HF 条件预算 tok/s | 生成轮实测 tok/s | HF 达成率 | 自身成本达成率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Count | 10.000 | 39.08 | 72.61 | 114.3 | 113.8 | 99.5% | 99.5% |
| Sky | 1.184 | 23.56 | 62.08 | 41.6 | 44.3 | 106.4% | 99.3% |
| Python | 1.939 | 33.22 | 85.28 | 44.5 | 51.4 | 115.5% | 99.5% |
| JSON | 3.765 | 30.59 | 80.92 | 75.9 | 55.4 | 73.0% | 99.5% |
| Chinese | 1.016 | 20.15 | 42.74 | 44.4 | 44.7 | 100.6% | 99.2% |

JSON 的 73% 不表示 27% 都耗在控制器上：其原生进度预算约 55.7 tok/s，与 55.4 的实测接近，
主要差异是原生与 HF 定下 token 的过程不同。超过 100% 的项同理。
Count 的端到端吞吐为 72.1 tok/s，不能把表中的 113.8 当作请求吞吐；prompt 和首块成本仍然存在。

固定初始热预览 W16 约 14.6 ms 不是整段去噪的平均 p。
本轮实际动态路由的 p 为 20–39 ms，整块 c 为 43–85 ms；直接以 14.6 ms 和一次 causal 9–12 ms
计算所谓上限会过于乐观。对于满块 W、平均每预览输出 k，可写成 `k/(p+k×c/W)`；
要胜过 causal 单步 t，需 `k > p/(t-c/W)`，前提分母为正且满块假设成立。
对 EOS、截断短尾应用完整 N/P/B 公式。
这里 t 是 causal 前向的事件区间；门槛用于诊断计算成本，不是端到端收益保证。

| W16 提示 | 原生可见 token/预览 k | 满块近似的盈亏平衡 k |
|---|---:|---:|
| Count | 10.00 | 7.16 |
| Sky | 1.29 | 3.63 |
| Python | 2.37 | 5.16 |
| JSON | 2.37 | 4.84 |
| Chinese | 1.03 | 3.15 |

这解释了当前样本中只有 Count 适合 denoise16；其他提示即便控制器完全免费，也不足以抵消多次预览和整块提交。
门槛随缓存容量、上下文和实现成本变化，不能固化成模型的普适常数。

另做 cap64、W16、2 warmup + 3 实测的计数快照诊断。各阶段逻辑 H2D 之和逐请求校验等于总计；
快照自身有开销，不混入主表。下列 GiB 均为每请求总量，不是每次预览的字节：

| 提示 | 可见 N | 预览 P / 块 B | advance GiB | preview GiB | verify GiB | 总 GiB |

这组数据与动态专家卸载造成额外成本的解释一致；尚未逐 kernel 隔离 attention、GDN、MMQ 和物理 PCIe 时间，
所以不把逻辑字节除以时间称为真实总线带宽，也不声称所有额外预览时间都来自 PCIe。

## 预览数值 A/B

只选 JSON W16、Count W32，共 48 行，比较 native、Torch conv、Torch GDN、Torch coreset、
组合替换，以及反量化权重后 Torch FP32 dense/MoE（分别保留/去掉 Q8_1 激活量化）。
参考也成对使用相同激活处理；另导出 native 的干净 KV/GDN 给参考，以排除不同 prefill 状态这一变量。
FP32 dequant+matmul 是诊断参考，尚未实现为服务模式，也没有把它作为新的性能路径。
使用 Q8 分支的 [诊断脚本](https://github.com/wenlive/FreeToken/blob/b49fafb/benchmarks/check_clover_preview_ab.py)，实际参数和 tensor 摘要见实验登记。

| native 与参考的首次预览 | 各自 prefill 的 argmax 一致率 | 共享 native clean 状态的一致率 |
|---|---:|---:|
| JSON W16 | 93.75% | 100% |
| Count W32 | 84.375% | 93.75% |

Count 共享状态下全 Torch + Q8_1 可到 100%、KL 约 .0100；但 JSON 同一变体的一致率降至 93.75%、KL 约 .0766。
Count 去掉激活量化的对应共享状态比较只有 78.125%、KL 约 .0565。只替换 coreset 与 native 相同。
因此不能判定“去掉 MMQ 激活量化即可修复”，也没有证明唯一根因是 GDN。
prefill 状态和预览算术都贡献差异；argmax 与 KL 也不总是同向变化。
小样本诊断不替代原有 C 验收，HF 去噪进度 4/15 与 NVFP4 两个 W32 差异继续列为未闭环。

每侧 25 次实测输出 ID 成对相同，独立 row gather 测试逐字节相同。该比较改变了自动规划后的缓存容量，
不是固定槽数下仅测 embedding 的微观代价；每侧一个进程，不能代替完整 ABAB 因果归因。
它支持“腾出容量后减少专家搬运”的解释，但不把 cap128 数据与 cap256 主表直接作前后速度比。

专家 host bank 载荷为 34,225,520,640 字节（31.875 GiB），不含额外 table。
进程 working-set 峰值 OFF/ON 为 34.51/35.48 GiB；这是进程指标，不是系统可用内存最低值。

独立资源诊断只测 Count、denoise32、cap64、auto .9、4K KV，1 warmup + 2 实测；
NVML 整卡采样覆盖模型启动及请求，含桌面。各配置不是五提示六模式的资源上界。

| off | 2292 | 13.19 | 13.22 | 14.32 | 34.56 |

NVML 驱动计数窗口 20 ms，实际最大采样间隔约 95 ms，峰值应读作采样最大值。
R0 的 15.71 GiB 来自不同的压力/多模式配置，不把两者相减当作同口径优化收益。
32K 固定2304槽/.95上下文扫描的 PyTorch allocated/reserved 峰值另为14.58/15.19 GiB；没有对应整卡采样，
不能套用上表的余量。自动规划解决已声明事务窗口的预算遗漏，不提供对其他进程、任意长 prefill 或任意桌面负载的显存隔离。
